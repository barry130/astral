## Confirmed local static findings

### AS01 — P2 — Rebinding a render template can delete it and update its deleted ID

**Evidence:** [MessageTemplateService.save](<../../../astral-system/src/main/java/com/astral/system/notify/MessageTemplateService.java#L116-L206>) checks conflicts, resolves `originalCode/originalScene`, removes old render rows on scene change, then retains `existingMail` with a nonnull ID and calls `updateById` for selected EMAIL/INAPP channels. The update boolean is ignored. [The public save DTO](<../../../astral-system/src/main/java/com/astral/system/dto/MessageTemplateSaveDto.java#L25-L29>) explicitly supports renaming/rebinding; [the public controller](<../../../astral-system/src/main/java/com/astral/system/controller/MessageTemplateController.java#L64-L69>) invokes this save method. [Render-template service implementation](<../../../astral-system/src/main/java/com/astral/system/mail/SysMailTemplateServiceImpl.java#L1-L10>) is ordinary ServiceImpl, without a local upsert override.

**Condition/cause/impact:** an existing render template is rebound from its old event to a different registered, presently unbound event; selected render channels retain matching old row objects. Removal happens before a deleted row ID is reused as an update target. Ordinary update-by-ID is not insertion: the save can complete with no surviving replacement row. This can make subsequent notification/template resolution fail despite save success.

**Counterevidence/boundary:** unchanged saves need not remove rows; target conflicts can reject before mutation; the SMS branch resets the deleted old SMS row to null and creates a new row, so SMS does not share this exact reuse cause. [Render schema](<../../../astral-schema/src/main/resources/schema/sys_mail_template.json>) was fully read; applied Flyway constraints, real generated mapper behavior, transaction rollback and row counts are UNTESTED. Requirement: registered scene/channel binding and persistent editable templates in the current notification guide.

**Next PUBLIC verification:** use the existing MessageTemplateController.save → actual transactional MessageTemplateService.save proxy with MessageTemplateSaveDto and isolated real rows. Rebind EMAIL and INAPP separately to an existing registered unbound event; assert saved rows and subsequent public notification publication resolve them. Include unchanged-save, conflict rejection/rollback, and SMS controls. Do not call a private rename branch or replace the service with a fake.

### AS02 — P2 — Supported code-only rename can conflict with its own old scene row

**Evidence:** [MessageTemplateService.save](<../../../astral-system/src/main/java/com/astral/system/notify/MessageTemplateService.java#L116-L157>) runs conflict checks before resolving the original identity; [checkCodeAvailable logic](<../../../astral-system/src/main/java/com/astral/system/notify/MessageTemplateService.java#L303-L342>) checks scene/channel with the new template code rather than excluding the original row identity. The DTO's original-identity fields are a current rename contract, not an invented operation.

**Condition/cause/impact:** rename a persisted render-template code while keeping its registered scene and selected channel. The old code differs from the new code and is counted as a scene/channel conflict; a valid rename is rejected. This is distinct from AS01's post-delete failure.

**Counterevidence/boundary:** identical code/scene saves and new templates do not satisfy the problematic condition. Genuine competing rows must still be rejected. Database execution and exact failure response are UNTESTED; current template uniqueness and editable-template contract apply.

**Next PUBLIC verification:** same actual controller/service/DTO seam; persist one row, change only templateCode with originalCode/originalScene supplied, and assert rename plus stable scene/channel uniqueness. Add a truly competing template control and verify body business code rather than assuming HTTP200 means success.

### AS03 — P2 — Daily quota checks do not reserve capacity before delivery

**Evidence:** [NotifyPublisher delivery sequence](<../../../astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L247-L280>) checks quota, delivers, then increments; [quota implementation](<../../../astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L327-L356>) performs separate GET and INCR. [Rule DTO dailyLimit/scope](<../../../astral-system/src/main/java/com/astral/system/dto/NotifyRuleSaveDto.java#L44-L48>) exposes per-recipient/global maxima.

**Condition/cause/impact:** two publications for the same positive-limit rule/channel/quota key both read below the limit before either increments. Both deliver; the counter subsequently exceeds the configured daily maximum. Atomic INCR after sending does not make the preceding check/reservation atomic.

**Counterevidence/boundary:** a sequential publication can be capped; dailyLimit=0 intentionally bypasses quota. Redis availability/deployment semantics and real concurrent sends are UNTESTED. [Current quota contract](<../../../AGENTS.md#L209-L230>) requires a daily limit, not merely an after-the-fact counter.

**Next PUBLIC verification:** registered event and existing NotifyRuleController public rule/publish surfaces → real NotifyPublisher.publish bean; positive GLOBAL and RECIPIENT limits with coordinated concurrent isolated deliveries. Keep the real publisher, actual async proxy in the async variant, and registered channel SPI boundary explicit. Assert delivered count, result failures and quota count; no external message is sent in an unapproved test.

### AS04 — P2 — Recipient-resolution failures can abort remaining rules/channels

**Evidence:** [NotifyPublisher.publish](<../../../astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L86-L123>) queries channels/recipients and calls recipient resolution outside the per-delivery catch; [ROLE expansion](<../../../astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L189-L225>) includes database queries. [publishAsync](<../../../astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L131-L145>) catches only at the outer job boundary.

**Condition/cause/impact:** a channel recipient lookup or ROLE expansion throws after publication begins. Exception propagation exits publication rather than returning that channel's failure result and continuing later configured channels/rules. The async outer catch prevents propagation to its caller but does not resume skipped deliveries.

**Counterevidence/boundary:** send/template exceptions inside the later delivery catch are already isolated. An initial total rule-database outage is not claimed to be recoverable per-item. No fault injection/runtime was executed. [Current per-rule/channel failure isolation](<../../../AGENTS.md#L209-L216>) is the direct requirement.

**Next PUBLIC verification:** two valid configured channels/rules through NotifyRuleController publication → actual NotifyPublisher; induce only the first recipient-resolution dependency failure, then assert a failure item and an attempted later valid delivery. Repeat through real async dispatch; success of an outer log statement is not proof of continuation.

### AS05 — P2 — Failed INAPP insert is reported as successful delivery and consumes quota

### AS07 — P2 — Missing permission domain falls back to side rather than domain

**Evidence:** [PermissionController domain fallback](<../../../astral-system/src/main/java/com/astral/system/controller/PermissionController.java#L201-L208>) takes the first code segment, whereas [PermissionChecker.domainOf](<../../../astral-auth/src/main/java/com/astral/auth/security/PermissionChecker.java#L327-L374>) skips a recognized side and selects domain. [PermissionController.create](<../../../astral-system/src/main/java/com/astral/system/controller/PermissionController.java#L83-L105>) accepts the fallback.

**Condition/cause/impact:** a permission such as admin:system:user:view is created with omitted/blank domain. It can be stored under admin instead of system, splitting domain-dependent catalog/list behavior from the canonical declaration semantics.

**Counterevidence/boundary:** an explicitly supplied correct domain masks this path; no claim that every generated/registered permission has a wrong domain. [Current domain requirement](<../../../AGENTS.md#L326-L345>) expressly prohibits deriving admin from the first segment. Schema for permissions and applied SQL constraints are NOTREAD/UNTESTED.

**Next PUBLIC verification:** existing PermissionController.create with Permission input through actual permission/super aspect and real Checker/StpInterface; omit domain, then use public detail/list/tree and compare with an explicit-domain control. Include user/all prefixes and already-normalized legacy input without private-helper tests.
