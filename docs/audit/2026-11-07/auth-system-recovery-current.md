## Spec axis — direct causal defects

### F1 — render-template rebind deletes a row, then updates its retained ID (P1, static logical defect)

[MessageTemplateController.java:64–69](<astral-system/src/main/java/com/astral/system/controller/MessageTemplateController.java#L64-L69>) exposes the save path to authorized template editors. [MessageTemplateService.java:131–184](<astral-system/src/main/java/com/astral/system/notify/MessageTemplateService.java#L131-L184>) loads `existingMail`, deletes its render rows when code or scene changes, but leaves the deleted objects in `existingMail`. For a retained EMAIL/INAPP channel it subsequently selects the same object, whose ID is still nonnull, and calls `updateById` rather than `save`. The update result is ignored, so the service can finish successfully after losing the render channel. The SMS branch explicitly clears `existingSms` after deletion and does not have that same retained-object path.

Fresh dependencies: [SysMailTemplateServiceImpl.java](<astral-system/src/main/java/com/astral/system/mail/SysMailTemplateServiceImpl.java>), [SysSmsTemplateServiceImpl.java](<astral-system/src/main/java/com/astral/system/notify/SysSmsTemplateServiceImpl.java>), [mail template schema](<astral-schema/src/main/resources/schema/sys_mail_template.json>), [SMS template schema](<astral-schema/src/main/resources/schema/sys_sms_template.json>). Both services are plain MyBatis-Plus services; the selected schemas have no soft-delete field. Ordinary delete/update semantics support this causal finding; real entity generation, SQL execution, transactions, and endpoint response were not exercised.

Lead verification condition: existing render template + available new code/event + retained render channel must preserve a persisted replacement after rebind and must not ignore an update of an already removed ID. Fix through an authorized implementation and public-service regression; no recovery patch was made.

### F2 — role-link PUT bypasses the role-change notification hook (P2, static dispatch defect)

[UserRoleController.java:92–105](<astral-system/src/main/java/com/astral/system/controller/UserRoleController.java#L92-L105>) performs `lambdaUpdate().update()`. The role-change event hook is in the distinct [UserRoleServiceImpl.java:86–101](<astral-system/src/main/java/com/astral/system/service/impl/UserRoleServiceImpl.java#L86-L101>) `updateById` override. The wrapper path does not call that override. [UserRoleChangeNotifier.java:26–89](<astral-system/src/main/java/com/astral/system/notify/UserRoleChangeNotifier.java#L26-L89>) constructs the before/after diff and publishes after commit; [NotifyEventRegistry.java:145–157](<astral-system/src/main/java/com/astral/system/notify/NotifyEventRegistry.java#L145-L157>) defines the event. Thus this PUT route can change the mapping without that notification preparation, unlike the service save/remove/assign paths.

**Not a permission-cache bypass**: class-level `RequiresSuper` remains and the controller still calls `PermissionCache.bumpVersion()`. The cache implementation was not independently re-read, and live authorization was not executed. Lead should verify changed role/user mappings trigger exactly the intended post-commit diffs while preserving whitelist updates and cache invalidation.

### F3 — failed INAPP insert is reported and quota-counted as successful (P1, static failure-propagation defect)

[InappServiceImpl.java:135–140](<astral-system/src/main/java/com/astral/system/notify/InappServiceImpl.java#L135-L140>) catches mapper insert exceptions, logs, and returns normally. [NotifyPublisher.java:263–277](<astral-system/src/main/java/com/astral/system/notify/NotifyPublisher.java#L263-L277>) treats that normal return as success, increases quota, and emits `PublishResult.ok=true`. A caught insert failure therefore appears successful despite no persisted notification. Main-flow failure isolation already exists at the publisher's per-delivery catch and async boundary; preserving that isolation does not require lying about delivery success.

Lead verification condition: inject an INAPP mapper failure through the real publisher/service path; the result must be unsuccessful, quota must not increase for a failed delivery, and other deliveries/business flow must remain isolated. No injected failure or runtime quota operation occurred here.
